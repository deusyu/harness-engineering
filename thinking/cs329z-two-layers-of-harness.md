## 论点

CS329Z 里 "harness" 出现得很密：第 1 讲的大纲把 "Optimization and harness" 列为基础主题，第 5 讲专门拆解开源 agent harness，HW1 的标题就是 *Building an Agentic Harness*。但它说的 harness 和本仓库的主语不在同一层。

用[对照表](se-to-agent-engineering-mapping.md)的三层主语来分：讲义教的是 **② agent 自身**——模型外那层运行时怎么搭（工具协议、循环、上下文、记忆、审批、护栏），客座讲座原样引用了 #47 的词汇表："agent harness 是让模型能作为智能体行动的系统"。本仓库从 #1 出发，关心的主要是 **① 人对 agent** 与 **③ 人对系统**——仓库即记录、机械化约束、熵管理、合并理念。截至写作时点，讲义对这两层几乎没有着墨。

但 HW1 的 starter 仓库本身，恰好是一个把 ① ③ 做到位的样板：它约束的对象是"学生 + 学生手里的编码智能体"这个组合。**这门课最值得本仓库学的 harness engineering 不在讲义里，在作业的工程结构里。**

## 二、讲义显式教的：agent harness 的设计空间

第 5 讲拆解的四个开源 harness，代表四种取舍：

| harness | 工具 | 历史与上下文 | 执行与终止 | 刻意不做的 |
|---|---|---|---|---|
| mini-SWE-agent | 只有 bash | 完全线性，每步只追加 | 每个动作独立 `subprocess.run`，没有常驻 shell | 其余一切工具 |
| OpenHands | （讲义未展开） | 每步一个 JSON 事件落盘，每次调用从事件重建上下文 | tmux 持久终端；同一动作和结果重复 4 次即自行停止 | — |
| Pi | read / write / edit / bash，系统提示词不到 1,000 token | 历史是树，可回到旧消息另开分支 | 以启动进程的权限直接执行，无审批 | 子智能体、计划模式、权限检查、待办清单、后台 bash |
| OpenClaw | （讲义未展开） | 身份由 AGENTS.md、SOUL.md、IDENTITY.md、USER.md、MEMORY.md 注入系统提示词 | 单一长驻 Gateway 进程接管所有聊天渠道；每 30 分钟心跳一次（回 NO_REPLY 保持沉默）；每晚 3 点把当天笔记整理进 MEMORY.md | — |

HW1 把这些取舍落成设计备忘录里必须逐题回答的问题：BM25 排序错在哪、工具调用用什么文本协议、模型说"我去查一下"却没调工具时循环怎么判停、检索结果给多长的片段与阅读窗口、超长终端输出给模型看什么、compaction 先丢什么且永不丢什么、记忆存什么及新会话开局带多少、确认模式下哪些调用免审批、沙箱在本机拦得住什么拦不住什么、整个 harness 的局限。其中"超长输出给模型看什么"一题直接列出业界的不同答案：mini-SWE-agent 原样透传；Codex CLI 截断，保留头尾；OpenHands、Gemini CLI、Claude Code 截断，并把全文写进文件、告诉模型路径。

这份清单可以直接当 harness 设计评审的提纲用。它比 #3 的组件清单多出来的，是每一项都要求写明"选了什么、为什么"。

## 三、作业隐式示范的：HW1 仓库本身就是一个 harness engineering 样板

HW1 允许学生用 Claude Code、Codex 等工具写作业，再用口试检查理解。所以 starter 仓库实际约束的是"学生 + 编码智能体"这个组合，它的结构与 #1 的六大概念、Böckeler 的 Guides × Sensors 基本一一对得上：

| HW1 的做法 | 对应的仓库概念 |
|---|---|
| 作业说明开头就把 harness 决策分成两类：**结构性决策**由课程定、由测试强制；**判断性决策**留给学生，每处标 "Design decision"，在设计备忘录里辩护。"复杂度不加分：过了测试、在备忘录里讲得通的策略，三行还是三百行都拿满分" | [机械化执行](../concepts/02-mechanical-enforcement.md)与人工评审的分工；本仓库的 C1–C14 加策展人类闸门是同一形状 |
| 测试只经 `adapters.py` 一个入口调用学生代码，类型签名和文档字符串就是权威规格；仓库里的文件逐个标注 provided / yours / read | [仓库即记录系统](../concepts/01-repo-as-source-of-truth.md)、地图而非手册 |
| "确定性测试就是我们要求的全部错误处理；不在测试里、也不在备忘录里的，一律不评分" | 规格边界显式化，[约束即产品](../concepts/07-spec-as-product.md) |
| `ScriptedLM` 回放固定回复，确定性测试零模型调用、零成本，却占自动评分的一半以上 | 计算性传感器：快、便宜、每次都跑 |
| 实时测试的阈值集中在 `thresholds.py`；正式评分换成同分布的留出数据，"只贴合公开标签、不贴合评分细则的提示词撑不住" | 推理性传感器，加上防 Goodhart |
| 模拟用户评测 = 程序化检查 + judge；judge 只看对话、工具调用和工具结果片段，陈述了工具结果里找不到的具体事实就判编造，模拟用户说"目标达成"不算证据 | #47 评结果不评路径；#33 过程合规 |
| LM 包装层自带缓存、成本账本和自设预算闸（超额直接抛 `BudgetExceeded`），并提醒"提示词或工具结果里出现绝对路径会让缓存每次失效" | #39 prompt caching；成本是一等约束 |
| 沙箱分四层（命令白名单、清空环境变量、超时与输出上限、系统级 jail），每层都写明拦得住什么、拦不住什么 | #50 先在环境层遏制；把安全层的盲区写成文档 |
| 护栏题故意让植入指令绕开正则 deny 规则："机械层拦不住，靠你的系统提示词和你在 run_terminal 外加的检查"；并规定工具输出里的文本不得改变模式、审批策略和 deny 规则 | 计算性约束的覆盖边界由测试显式标出 |

两个细节值得单独记。

**约束要放在机制里，不能只放在记忆里。** 第 7 讲开场引用了一起真实事故：2026 年 2 月，一位用户叮嘱 OpenClaw "先建议哪些邮件该归档或删除，等我发话再动手"；真实收件箱太大，触发了 compaction，这句指令在压缩中丢失，agent 随即开始清空收件箱（当事人自述，媒体未能独立核实）。HW1 对这类失败给了两道带测试的答案：compaction 必须保证"用户陈述过的约束在原消息离开上下文后依然可用"；确认模式下，非只读工具执行前由**代码**调用 `approve()`，不依赖模型记得要先问。前者把约束留在上下文里，后者干脆不让约束依赖上下文——后者才是本仓库[机械化执行](../concepts/02-mechanical-enforcement.md)的意思。

**人类闸门设在理解上，不设在代码上。** 第 1 讲引用 Anthropic 的随机对照实验：学一个新 Python 库时，用 AI 辅助的工程师在随后的测验里低 17%，差距集中在调试。课程的回应不是禁用 AI，而是"允许用，口试验"。作业说明的致谢也写明，HW1 是"在 Claude Fable 5.1 的大量帮助下设计和构建的"——出题方自己就在用编码智能体，于是把结构性约束全部写成测试，只把判断留给人。这和本仓库把人类闸门设在"收录决策"上是同一个思路：机器能验证的交给机器，人只守机器验证不了的那一道。

## 四、与仓库既有判断的三处张力

### 1. harness 重要，但重要在哪一维？

#35 用榜单方差归因得出 "harness 效应 ≈ 模型效应"。第 5 讲指定阅读 HarnessTax 给出另一幅图：Claude Code、Codex CLI、Pi 三个成熟 harness 搭配七个模型，在 SWE-bench Lite 与 Terminal-Bench 2.0 上各抽 30 题，harness 对成功率的平均影响在 ±2%（SWE-bench Lite）到约 ±5%（Terminal-Bench 2.0）以内，成本却能差到两倍：Claude Fable 5 在 Claude Code 里每题 $1.33、成功率 97.8%，在 Pi 里每题 $0.67、成功率 96.7%。Claude Code 的初始上下文平均是 Pi 的 10 倍以上。

两者可以同时成立：#35 的样本覆盖 28 个 harness，质量跨度大；HarnessTax 只取了成熟的那一端。合起来读是：**harness 在"能不能做成"上的差距随成熟度收敛，在"花多少钱做成"上的差距不收敛**。仓库里"harness 很重要"这句话，应拆成成功率和成本两句分别说。HarnessTax 自己的保留意见也要带上：每个基准只有 30 题，两个基准都可能在训练中见过。

### 2. "可移植性"至少是四个问题

仓库长期挂着"跨模型可移植性"缺口。把课程材料放进来，会发现它不是一个问题：

| 问题 | 证据 | 目前的答案 |
|---|---|---|
| 同一模型换 harness，能力还在不在 | HarnessTax：12 组对比里有 9 组，成功率最高的是"别家" harness | 基本在 |
| 同一模型换 harness，**约定**还在不在（工具 schema、调用格式） | #62；第 11 讲"SFT 会让模型同时模仿能力和 harness，且分不清哪部分是哪部分"，对策是训练时轮换 harness；观察项 MCP vs CLI + DCAS（微调数据集中于单一 scaffold 导致锁定） | 不在，且模型训得越好越顽固（#62） |
| 同一套 harness 工件换模型，收益还在不在 | #75：冻结工件跨 GPT 与 Qwen 迁移 12 行全正；#35：收益不保序 | 方向多半在，幅度不保序 |
| 同一句提示词换模型，还过不过阈值 | HW1 作业说明："在一个模型上 20/20 的提示词，换个模型只有 11/20，两个方向都是如此" | 不在 |

第三行与第四行表面矛盾。一个可证伪的解释：**知识型工件（技能、工具、流程）可迁移，措辞型调参不可迁移**——前者编码的是任务结构，后者贴合的是某个模型的决策边界。第一行与第二行也不矛盾：#62 说的格式摩擦，如果被重试或 strict 解码吸收，就不会体现在成功率上；HarnessTax 没有报告格式错误率，这是可以补测的空白。

### 3. 事实源从规格移向评测？

客座讲座给了一组对照：传统软件里代码是事实源，确定、靠演绎；agent 世界里评测是事实源，随机、靠经验。随后追问："规格的写作者是软件工程师，评测的写作者是谁？"这与[约束即产品](../concepts/07-spec-as-product.md)形成张力：产品到底是 spec 还是 eval？

我的读法是两者分属前馈与反馈：spec 是 guide，eval 是 sensor。讲座的主张换成本仓库的话说，是 sensor 正在变成更权威的那一方——两者冲突时，以 eval 的判定为准。讲座随后给出的工程纪律，正好是本仓库评测线（#47、#59、#69）还缺的一块：**任务即软件**。任务改动按语义化版本分三档，分别对应"要重跑 agent""只需重新判分""旧结果可直接复用"；基准跑 CI；用"作弊 agent"主动找 reward hack；每一行结果都附完整收据（轨迹、日志、产物、奖励）。

## 五、课程没覆盖的（截至写作时点）

已发布的讲义没有涉及本仓库主线上的这些内容：仓库即记录系统与 AGENTS.md 作为地图、用 linter 与架构测试检验编码智能体的产物、熵管理与垃圾回收、高吞吐下的合并理念、loop engineering（#41–#43、#55、#72）、软件工厂（#63–#65）、组织级采纳（#73）。这不是课程的缺陷——它的对象是"造一个 agent"，不是"让 agent 在你的代码库里可靠工作"。后续"编码智能体"一讲的指定阅读包括 #58 与 Claude Code 最佳实践，可能补上一部分，发布后值得回看。

## 开放问题

1. **判断性决策能不能机械化一部分？** HW1 的测试只拒绝"明显失败"的选择，其余交给备忘录。本仓库的 C13 已经是同一思路的半步：零插图声明无法证伪，就要求留下核对痕迹。设计备忘录里哪些问题可以改成"必须留痕的字段"，哪些只能靠人读？
2. **HW1 适不适合当 practice/ 的第二个实验？** 它把 Guides × Sensors 的环境现成搭好了（MIT 许可），自带确定性测试、阈值、模拟用户评测与成本账本，正合 practice/ "人只写约束、代码全由智能体生成"的约定。它与 Ralph Demo 互补：Ralph 验证的是循环本身，HW1 验证的是循环里的每个零件。代价是课程的荣誉准则：学期内公开完整解答等于给在读学生递答案。
3. **"知识型工件可迁移、措辞型调参不可迁移"能不能测？** 一个最小实验：取 HW1 的 priority 题，分别把"规则表加示例"和"调过措辞的提示词"迁移到另一个模型，看哪一种掉得少。

## 结论

CS329Z 是一门讲"怎么造 agent"的课，它对 harness 的处理扎实、可操作，尤其是把 harness 拆成一组必须逐项辩护的设计决策。对本仓库而言，它的价值不在定义——定义与[概念页](../concepts/06-harness-definition.md)一致——而在两处：一是 HW1 的工程结构，给"结构性决策交给测试、判断性决策交给人"提供了一个现成、可复刻的样板；二是课程材料里的证据（HarnessTax、对 harness 过拟合、提示词跨模型不迁移），把仓库里"harness 很重要""可移植性有缺口"这两句笼统的话，拆成了可以分别检验的几句。
